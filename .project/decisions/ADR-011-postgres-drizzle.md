# ADR-011: PostgreSQL through Drizzle ORM for transactional data, starting with credits and payments

Date: 2026-09-17
Status: accepted

## Context

The API persists everything in JSON files under `.data/` (`FileCreditLedgerStore`, `templates.store.ts`, …). Each write reads the whole file, mutates it and rewrites it, with no transaction and no lock. That was acceptable for a demo; it is not once real money flows in:

- the credit balance is the `balanceAfter` of the last ledger entry, so two concurrent consumptions (or a consumption racing a Stripe webhook) can both read the same balance and one of the writes is lost;
- webhook idempotency relies on scanning the user's history in memory;
- the admin is about to manage a catalogue of credit offers synchronised with Stripe, which needs constraints (one featured offer, unique Stripe price ids) that files cannot enforce.

PostgreSQL 16 already runs in every compose stack (local, staging, production) and is backed up nightly, but no code uses it.

## Decision

- Use **PostgreSQL** for credit offers, credit orders (Stripe checkout) and the credit ledger. Other JSON stores move later, one module at a time.
- Access it through **Drizzle ORM 0.45** (`drizzle-orm`, driver `pg` / node-postgres), schema in TypeScript under `apps/api/src/database/schema/`.
- Migrations are **SQL files generated by `drizzle-kit generate`** into `apps/api/drizzle/`, reviewed like code, and applied by `src/database/migrate.main.ts` **before the API process starts** in the container. A failing migration stops the rollout.
- Stores depend on the driver-agnostic `Database` type (`PgDatabase<PgQueryResultHKT, schema>`), injected through the global `DatabaseModule` under the `DATABASE` token.
- Store and SQL tests run against **PGlite** (`@electric-sql/pglite`, the Postgres engine compiled to WASM, dev dependency only) with the real migrations applied: same SQL as production, no Docker needed in CI.
- `GET /ready` checks the database; `/health` stays a liveness probe.
- On Dokploy, clients reach Postgres through a **per-environment alias** (`${POSTGRES_HOST}`), never the bare `postgres` service name that staging and production share on `dokploy-network` (see docs/deploy.md §4d).
- Legacy JSON data is imported once per environment by idempotent scripts guarded by the `data_imports` table.

The Stripe integration moves from hand-written `fetch` calls to the official **`stripe` Node SDK** in the same effort; it is recorded here because it lands with the same billing rework: typed API, signature verification via `webhooks.constructEvent`, maintained API version pinning.

## Consequences

- The API now needs `DATABASE_URL` (mandatory in production) and the Docker image ships `apps/api/drizzle/`.
- Balance updates become transactional (`SELECT … FOR UPDATE` on a per-user balance row).
- Two persistence styles coexist until the remaining JSON stores migrate.
- Schema changes require `pnpm --filter @cvforge/api db:generate` and a committed migration.

## Alternatives considered

- **Keep JSON files with a file lock**: rejected, still no constraints or atomic multi-row updates, and it does not scale past one API instance.
- **Prisma**: rejected, generated client and query engine add a build step and weight to the image; declarative schema is less explicit about the SQL we need to review for money-related tables.
- **Kysely / raw `pg`**: viable, but Drizzle gives the same SQL-level control plus schema-driven migrations.
- **Testcontainers for store tests**: rejected for now, requires Docker in every test run; PGlite covers our SQL surface.
